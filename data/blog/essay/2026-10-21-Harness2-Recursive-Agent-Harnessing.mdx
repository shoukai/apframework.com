> 双层递归、可执行经验与 DeerFlow 的工程接入

一个 Agent 接到新的资料研究任务，明明能读取文件、搜索和写报告，却反复打开同一份材料，最后交出一篇看似完整、引用却没有核对过的文章。工程师可以补一条提示词，也可以加一个引用检查脚本。但任务每变一次，就得重新发现问题、重新猜测改法。如果这些尝试只留在聊天记录和临时分支里，系统的维护成本会随着任务种类一起增长。

Google Cloud AI Research 的 [Harness² 项目](https://harness2.github.io/)研究的正是这件事：**模型权重保持固定，让 Agent 在执行新任务时调整模型周围的 Harness，并把这次调整得到的证据用于下一次调整。**论文把这个过程称为 recursive agent harnessing。其目标不只是为当前任务找到一份更合适的执行配置，也包括改进“以后如何修改执行配置”的过程。[论文与摘要](https://arxiv.org/html/2610.14224)、[官方仓库](https://github.com/google-research/harness2)

这个方向值得关注，也容易被误读。Harness² 的在线反馈是执行行为的对比，不等于任务正确性的证明；它开源的是能运行的研究流程，不是已经具备业务回归、隔离 Worker 和生产发布能力的通用服务。下面先沿论文原图解释方法，再讨论如何把它接到已有 DeerFlow 执行器上。

## 1. 开放世界任务为何让 Harness 难以维护

这里的 Harness，可以理解为模型执行任务时依赖的提示词、记忆、工具指引、Skills、脚本、委派方式和运行控制。它决定模型看见什么、能做什么、什么时候调用工具，以及结果如何变成交付物。过去讨论 Agent 工程时，我更常把它放在 framework、runtime、harness 的分层中：框架提供编排抽象，运行时负责实际执行，Harness 是围绕模型组织能力与约束的可调整部分。具体项目的边界未必完全一致，本文采用这个操作性定义。[相关阅读：DeepAgents 深度解析](https://apframework.com/blog/essay/2025-10-25-DeepAgents)、[论文 §1–2](https://arxiv.org/html/2610.14224)

让 Harness 自行修改，首先碰到两个问题。其一，新任务在设计阶段没有出现过，在线执行时往往没有现成答案或可靠评分器。修改一份 Skill 以后，系统很难立即得到“分数提高了”的监督信号。其二，某个任务中好用的执行配置可能包含大量领域细节；直接带到下一任务，未必能带来同样收益。论文据此把关注点从“保存一份成功配置”，推进到“保存这份配置为什么被提出、怎样被试过、观察到了什么”。[论文引言](https://arxiv.org/html/2610.14224)

本文用一个**假设场景**贯穿机制说明：Agent 根据多份材料生成带引用的研究报告。基线执行可能出现重复读取、关键材料漏看、引用核对不足。这里没有真实业务实验，也不会为示例编造提升分数。它只用于说明：没有标准答案时，怎样让一次 Harness 修改仍然有可检查的依据。

## 2. 从论文原图理解 Harness²：两层递归如何连接

![Harness² 论文 Figure 3：左侧任务级递归依次包含基础执行、通用与领域候选、候选探测和组合；右侧经验反思更新改进 Harness，并引导下一任务。](/static/images/2026-10-21-Harness2-Recursive-Agent-Harnessing/harness2-paper-figure-3.png)

*图 1：Harness² 的双层递归流程。图源：Ruiyao Xu 等，《Harness²: Recursive Agent Harnessing for an Open World》，arXiv:2610.14224v1（2026），原论文 Figure 3；[论文图注](https://arxiv.org/html/2610.14224)、[原图文件](https://arxiv.org/html/2610.14224v1/harness2_main_new.png)、[项目官网](https://harness2.github.io/)。图片内容未修改；论文页面标注 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)。*

这张图最好按箭头读，而不是只看中间的几个角色。蓝色区域处理当前的 **Task t**，紫色区域处理下一次改进将参考的经验。它们相连，但保存和传递的对象不同。[论文 §2 与 Figure 3](https://arxiv.org/html/2610.14224)

**第一步，左侧的 Agent Executor 用 Initial Harness 跑当前任务。**它产生轨迹（trajectory）与交付物（output）。轨迹可以展示是否读取了材料、何时调用工具、在哪一步重试；交付物能展示报告、文件或回答本身。基础执行揭示的是当前 Harness 的行为，单看一次运行还不能判定答案正确。

**第二步，Harness Editor 给出两个不同范围的候选。**图里的 Invariant 指跨领域可能重现的代理性缺陷，比如规划顺序混乱、无效工具调用、上下文管理不当；Domain 指当前领域的知识、流程与约束。两个候选都是对可执行 Harness 文件的编辑。用假设的研究报告任务看，前者可以规范材料清单与阶段性检查，后者可以加入引用核对 Skill 和确定性脚本。

**第三步，Candidate Probes 让两个候选在同一个任务上执行。**运行时尽量匹配模型与环境条件，再比较各自轨迹、交付物和基础执行。假如某个候选减少了重复读取，却让 Agent 跳过最终核对，这就是一个需要带进组合阶段的回归观察。对比为“编辑引起了什么行为变化”提供证据；它没有自动产生正确答案验证器。

**第四步，Harness Composer 读取候选、文件差异和执行证据，形成 Final Harness。**它可以合并有依据的修改、改写冲突的部分、仅采纳其中一个，或保持原配置。组合后的 Harness 还会执行一次，并连同决策依据留下记录。图中的 Final Harness 指当前任务被采用的版本；论文用星号表示“被选中”，不表示数学上的最优或已经通过独立业务验收。[论文 §2.2](https://arxiv.org/html/2610.14224)

**第五步，右侧的 Experience Reflector 回看完整改进过程。**它把可执行配置与有对比证据支持的经验写入 Improvement Harness 的库中。底部箭头 “Move to the next task” 容易产生误解：论文下一任务仍从公共基础执行 Harness $H_0$ 出发，先前任务的执行配置并不自动成为新默认值；更新过的经验库会引导新的提案与组合。[论文 §2.3](https://arxiv.org/html/2610.14224)

这就是标题中平方的含义：一层改进当前任务的执行方式，另一层积累“怎样改进执行方式”的经验。两层之间靠执行记录连接。模型参数、各阶段提示指令和决策规则在论文设定中保持固定；持续变化的重点是经验库。

### Harness² 实际允许修改哪些东西

论文把执行 Harness 拆为八类可编辑的文件级组件。它们覆盖的不是同一种能力，因此在业务接入时也不应全部塞进一条长系统提示词。[论文 §2.1 与 Appendix D.3](https://arxiv.org/html/2610.14224)、[官方 README](https://github.com/google-research/harness2/blob/main/README.md)

| 作用位置 | 可编辑组件 | 主要影响 | 接入时需要关注的边界 |
|---|---|---|---|
| 上下文构建 | 系统提示词、护栏、记忆 | 任务要求如何进入上下文，哪些约束在每次调用时生效 | 长度、覆盖范围、与运行时原有指令的优先级 |
| 工具接口 | 工具指引、Skills | 如何选择工具，何时读取专项流程 | Skill 的发现与加载方式、工具参数兼容性 |
| 编排与委派 | 子智能体 | 任务如何分工，哪些资料进入独立上下文 | 并发、上下文成本和结果回收 |
| 确定性扩展 | 脚本 | 把核对、转换、计算等稳定步骤交给程序 | 权限、依赖、沙箱与输入输出契约 |
| 工具循环控制 | 插件或中间件 | 在调用链中检查或强制行为 | 与执行器内核耦合更深，需独立验证 |

文件级拆分使编辑、比较和版本管理变得具体。执行器是否真的按指定版本加载这些文件，是后面业务集成的第一道验收题。

## 3. Propose–Probe–Compose：行为对比怎样指导一次修改

论文把一次任务内改进写成 Propose–Probe–Compose。它的价值在于把“我觉得可以加一句提示词”变成一条有目标、有运行记录、有取舍理由的编辑链。[论文 §2.2](https://arxiv.org/html/2610.14224)

**Propose：先定位缺陷，再提出两种范围不同的修改。**基础运行、当前任务、已有 Harness 和经验库一起交给编辑器。通用候选处理跨任务可能重复出现的规划、工具使用、上下文或委派问题；领域候选处理当前领域的程序、格式或约束。候选可以复用经验库组件，但任务事实仍要按当前材料核对。对报告案例，通用候选若提出“先建立材料清单再写作”，领域候选若提出“引用必须能回溯到原文件页码”，两者要各自落实到真实可加载的组件文件。

**Probe：让修改后的 Harness 真正执行同一任务。**只阅读 diff 无法知道 Agent 是否照做。Probe 记录候选运行中的动作与观察，再与基础执行作对照：重复读取是否减少，引用核对是否发生，脚本是否成功完成，是否出现新的提前结束或额外调用。这里的匹配条件包括同一任务、模型和环境配置；即便如此，模型采样仍可能造成波动。一次有利轨迹只能支持一个有限判断，不能直接证明效果会稳定迁移。[论文 §2.2.1 与 Appendix F](https://arxiv.org/html/2610.14224)

**Compose：把证据转为具体文件决策。**组合器不必在两个候选之间二选一。例如，通用候选提高了材料覆盖率，而其中某条护栏令输出中断；领域候选改善了引用核对，但增加了无意义的全量复读。组合器可以保留前者的材料清单与后者的核对脚本，删去引起回归的规则，并记录这些选择对应的观察。新的组合配置还要再次执行，形成下一条可检查的轨迹。

可用的判断链是：**观察到的缺陷 → 编辑的组件与意图 → 同任务运行中的变化 → 保留或舍弃的理由**。其中最后一环很关键。如果日志只写“新版本更好”，既无法复盘，也很难让后续任务知道适用条件。把行为对比写成任务正确性结论，则越过了证据本身的范围。

论文给出了一个真实的 [JobBench 案例（Figure 9）](https://arxiv.org/html/2610.14224)，恰好把这条链串起来。基线轨迹显示，Agent 没有对多份源文件中的数字做核对，也没有在写完后重新打开交付物检查。通用候选增加了盘点输入、追踪数字来源和回读文件的流程约束；领域候选增加了处理日程、场地、人工与预算文件的专项 Skill，以及数字格式的工具指引。Composer 根据候选执行证据保留了两边的四处修改，组合后重跑补齐了备忘录缺失的章节。论文的**事后基准评测**给出 43.1→77.8 分。这个分数帮助读者理解案例效果，却没有在当时作为在线编辑器可见的反馈。这里的关键变化，是把“写完文件”推进为“文件中的数字可追溯、文件本身可复查”。

任务级递归还可以扩大预算。**Parallel** 模式在同一轮收集更多通用和领域候选，分别组合多个后继配置，扩大探索宽度；**Sequential** 模式连续运行多个改进步骤，让下一步继承前一步配置和累积执行证据，增加精炼深度。论文中的 $k$ 控制预算；$k=1$ 时两种方式退化为同一个基础步骤。$k>1$ 时，最终选择器从既有交付物里选一个，不重新综合新内容。更多探索通常意味着更多模型调用、运行时间和费用；论文只研究了有限预算范围。[论文 §2.2.2、Appendix F](https://arxiv.org/html/2610.14224)

## 4. 第二层递归：积累可以再次执行的改进经验

如果每个任务都只留下最终交付物，下一个任务仍要从头推测改法。Harness² 保存的是一次改进的完整记录：基础执行、候选修改、探测结果、组合决定和最终采用的配置。任务结束后，Experience Reflector 从中挑出有行为证据支持的教训。[论文 §2.3](https://arxiv.org/html/2610.14224)

经验库条目包括可执行 Harness 组件，以及记录适用场景、教训与支持证据的 `EXPERIENCE.md`。索引帮助后续改进会话按需查看相关条目。证据不足时，反思阶段可以不新增经验；“本次选中了某个输出”本身不足以证明这个修改可以迁移。这个设计让经验既有文本解释，也有能被再次装载、编辑和探测的文件。[论文 §2.3](https://arxiv.org/html/2610.14224)

论文对复用的测量也提示了一个细节：经验库里的文件更多被**改编**，而不是被整份复制。补充实验中，按基准不同，约 22%–47% 的已修改文件能找到可追溯的库内内容；真正保留库条目一半以上行数的文件只有 2%–10%。这与“任务仍从公共配置起步”的机制一致：库提供可检查的起点和适用经验，新任务仍需要针对自己的材料重新编辑、探测。[论文 Appendix E.2](https://arxiv.org/html/2610.14224)

由此要分清四种常被混在一起的资产：

| 资产 | 服务于什么 | 何时变化 |
|---|---|---|
| 当前任务的运行状态 | 让执行过程继续，保存中间文件与会话上下文 | 随任务推进变化 |
| 业务事实和用户偏好 | 帮助 Agent 理解特定业务或用户 | 经事实核对和权限规则更新 |
| Harness 改进经验库 | 指导下一任务怎样提出、探测和组合修改 | 当前任务结束后，基于对比证据更新 |
| 生产默认配置版本 | 决定真实业务流量运行哪份 Harness | 经独立回归和发布决策后变化 |

论文讨论的是第三项；第四项属于本文后面提出的生产工程层。任务内采用的配置可以进经验库，但不应因此自动覆盖线上默认版本。也正因为下一任务从 $H_0$ 开始，经验库中旧组件的复用需要先判断新任务是否相似、约束是否仍成立，再由提案阶段选择性引入。[论文 §2.3](https://arxiv.org/html/2610.14224)

## 5. 实验结果支持了什么

论文在三个专业基准上评估：WorkBuddy-Bench 覆盖 Code、Web、Office 交付物，JobBench 覆盖较长流程的职业任务，LAB 是法律工作基准，表中的 Partial 表示按评估条件统计的部分通过率。主结果是三次不同任务顺序运行的均值；执行模型为 Gemini 3.5 Flash 和 GLM-5，初始执行 Harness 为 OpenCode 或 Codex，默认编辑器为 Claude Opus 4.8。下表选取同一轮 $k=1$ 的几个配置，避免把不同指标拼成一个“总提升”。[论文 §3、表 1–2](https://arxiv.org/html/2610.14224)

| 基准与指标 | 执行模型 / 初始 Harness | 基础配置 → Harness²，$k=1$ | 增益 |
|---|---|---:|---:|
| WorkBuddy-Bench，三领域平均分 | Gemini 3.5 Flash / OpenCode | 72.4 → 77.5 | +5.1 分 |
| WorkBuddy-Bench，三领域平均分 | GLM-5 / OpenCode | 64.2 → 75.7 | +11.5 分 |
| JobBench，任务得分 | Gemini 3.5 Flash / OpenCode | 31.5 → 36.0 | +4.5 分 |
| LAB，Partial 条件通过率 | GLM-5 / OpenCode | 59.6% → 71.4% | +11.8 个百分点 |

这些数字说明：在论文的任务流与执行环境里，一轮基于对比证据的 Harness 修改，能给不同模型和基准带来增益。它们没有给 DeerFlow 或任何特定业务任务提供收益预测。论文还报告，WorkBuddy-Bench 上 Gemini 3.5 Flash / OpenCode 的平均分在并行 $k=5$ 时由 $k=1$ 的 77.5 增至 80.8；增加预算有效，但要算上编辑器和候选执行的成本。[论文 §3–4](https://arxiv.org/html/2610.14224)

另外两组结果有助于理解“双层递归”是否有价值。去掉经验库后，WorkBuddy-Bench 的对应分数从 77.5 降至 74.4，JobBench 从 36.0 降至 34.2；说明在该实验设置中，跨任务经验确实影响后续修改。把 JobBench 积累的库用于 WorkBuddy-Bench 的一次修改，在 Code、Web、Office 三个子集分别带来 0.6、0.5、2.9 分增益。论文明确指出后一项是回顾性迁移测试，不能写成真实在线部署后的持续学习成绩。[论文 §4 与表 3](https://arxiv.org/html/2610.14224)

还有一条容易被放大的结论：论文展示过相对弱一些的执行模型，在改进后的 Harness 下超过更强模型的基础配置。这证明 Harness 影响很大；它没有证明“改 Harness 总能替代换模型”。在 JobBench 上，Gemini 与 GLM-5 的增益排序就不同。论文自身也指出，执行对比受随机性和共同模型偏差影响，不保证结果正确或能迁移到新任务。[论文 §3–4、Appendix F](https://arxiv.org/html/2610.14224)

“工具调用更可靠”也不等于“调用次数总会更少”。在 Gemini 3.5 Flash / OpenCode、$k=1$ 的实验里，论文记录三个基准的工具错误率都下降；但 JobBench 的平均调用数从 27.4 增到 32.8，LAB 从 20.8 增到 25.2。多出的步骤可能用于核查，不能只按调用次数判断好坏。补充失败分析还列出九个相对基线退化的案例：选择器有时选中较弱交付物，候选也可能共享同一个错误前提；输出波动和评测缺失进一步增加归因难度。这些反例说明，Probe 的执行对比需要连同不确定性一起保存。[论文 Appendix E.4、E.6](https://arxiv.org/html/2610.14224)

## 6. 能直接用到什么程度：把 Harness² 做成独立进化服务

[官方仓库](https://github.com/google-research/harness2/blob/main/README.md)已经交付可运行代码，支持并行与顺序递归、OpenCode 和 Codex 执行器，以及 JobBench、LAB、WorkBuddy-Bench 三个适配器。仓库提供不需模型凭证的本地 demo：它使用确定性编辑器和真实 Python 执行，适合看懂流程；模型驱动的基准运行仍需相应环境与模型配置。仓库也提供运行记录、结果和恢复机制。它可以作为方法核心复用，但并未把业务 API、分布式实验 Worker 或生产发布流程一并交付。[官方 README：安装、实验与结果](https://github.com/google-research/harness2/blob/main/README.md)

适配其他 Harness，要完成两件事。**业务任务适配**负责列出任务、提供真实输入与材料、抽取交付物、导出可读轨迹、声明领域与任务约束。**执行框架适配**负责定义可编辑组件的文件结构，把候选文件准确装入目标执行器并校验。源码中的 `BenchmarkAdapter` 与 `SubstrateLike.surface()` 给出了这两个方向的接口；`execute(task_id, harness_dir, run_id, timeout)` 返回运行目录，评测 `score()` 的接口说明则把打分放在最终选择提交之后。因此，离线评测分数不能被写成 Harness² 在线 Compose 的反馈。[适配协议源码](https://github.com/google-research/harness2/blob/main/harness2/core/spec.py)

对目前“Octop 与 DeerFlow 独立执行、按任务路由”的结构，我建议让 Harness² 保持独立：业务路由器继续决定哪一个执行器承接任务；进化服务负责提出和比较候选；被选执行器的实验 Worker 负责把候选配置跑起来。第一阶段只接 DeerFlow，协议成熟以后再增加 Octop 适配器。下图是**本文的工程方案**，不是论文或官方仓库的现成部署图。

“独立”不一定意味着第一天就拆成多个微服务。先在一个进化服务里封装提交、查询、取消、预算与幂等；执行 Worker 可单独扩容。Harness² 核心目前以候选 Harness 目录和运行结果目录为主要接口，远程 Worker 因此需要一个桥接层：上传任务快照与候选包，执行后把结构化轨迹、交付物和必要文件落回可追溯的运行目录。这个目录契约跑通后，再考虑分布式存储和服务拆分。[适配协议源码](https://github.com/google-research/harness2/blob/main/harness2/core/spec.py)、[仓库运行说明](https://github.com/google-research/harness2/blob/main/README.md)

## 7. 先接 DeerFlow：把一次实验执行做成可比较的协议

DeerFlow 已有可嵌入的 `DeerFlowClient` 入口、配置、技能选择与流式事件；这些能力适合承接一次实验执行。接入时最重要的不是让编辑器先自动写提示词，而是证明“指定候选文件在一次独立执行中真实生效，并且它与基础执行的条件可比较”。当前公开源码中的客户端会缓存构造后的 Agent 与部分配置，配置对象也可能存在进程级状态；仅换一个 thread ID，不能作为配置和记忆完全隔离的证据。[DeerFlowClient 源码](https://github.com/bytedance/deer-flow/blob/main/backend/packages/harness/deerflow/client.py)、[配置说明](https://github.com/bytedance/deer-flow/blob/main/backend/docs/CONFIGURATION.md)

我会把第一版可编辑范围收敛到**提示词补充、Skills、检查脚本**。这几类组件较容易版本化、装载与验收。中间件、子智能体和更深的工具循环改动先留在候选范围之外，等执行协议、依赖与回归稳定后再开放。收敛编辑面是工程取舍，不是 Harness² 方法本身的限制。

| 工作位置 | 第一阶段要交付什么 | 验收时看到什么 |
|---|---|---|
| DeerFlow 配置适配层 | 版本化配置包、固定加载入口、组件校验 | 本次运行实际加载的文件列表与哈希，与请求版本一致 |
| 任务适配层 | 任务输入、材料清单、领域标签、交付物抽取规则 | 同一任务快照能重复提交，生成相同的初始输入 |
| 实验 Worker | 独立进程或容器、超时取消、资源回收 | 两个候选不会共用工作目录、checkpoint、配置缓存或可写记忆 |
| 证据转换层 | 统一工具动作、观察、错误、交付物和用量格式 | Compose 能看到候选改了什么、实际做了什么 |
| Harness² 桥接层 | `BenchmarkAdapter`、可编辑 Surface 与远程执行代理 | 能完成基础执行、两个候选探测、组合后执行与经验记录 |
| 运行管理 | run_id、任务状态、预算、版本和证据索引 | 任何一次结论可回溯到输入、环境、代码版本与输出 |

快照要包含任务输入、附件、可读的初始记忆、工具版本、模型参数和执行器版本。Worker 至少隔离文件目录、checkpoint、配置实例、缓存与记忆写入。若工具连接数据库、邮件或外部业务 API，容器只能隔离本地进程，不能撤销已经发生的外部副作用；这些工具需要测试租户、模拟接口或可恢复的测试数据。相同快照控制的是初始条件，不保证随机模型产生逐字相同的轨迹。

每次运行最好再留一份简短的 **run manifest**：任务快照哈希、候选 Harness 哈希、实际加载哈希、模型与执行器版本、工具环境版本、run_id、轨迹位置、交付物位置、结束原因和用量。这里特别要同时记录“请求加载什么”和“真正加载了什么”；否则缓存造成的配置串用，会被误判为某个候选无效。这个 manifest 是本文建议新增的证据协议，不是 Harness² 仓库已经定义的通用服务格式。

在自动改进前，先由工程师手写两份候选配置，让 DeerFlow Worker 按同一任务快照分别执行，检查实际加载哈希、轨迹和产物。若这一步无法复现候选差异，接上自动提案只会放大不可解释的噪声。完成协议验证后，再把 Harness² 的提案、探测、组合接到同一入口。这样，业务生产路由可以继续工作，进化任务在旁路积累证据。

## 8. 让改进进入生产：回归、发布与总成本

Harness² 的 Probe 回答的是“某次编辑对当前任务的执行产生了什么影响”。业务生产还需要另外回答：“没有参与这次编辑的任务是否退化？关键规则是否被违反？费用和延迟是否可接受？”因此，我建议把**候选采纳、经验保留、生产发布**作为三个独立决策。前两个可以主要依据论文的行为证据；生产发布要引入独立任务集、业务验收与版本审批。[论文 Appendix F](https://arxiv.org/html/2610.14224)、[相关阅读：验证与测量](https://apframework.com/blog/essay/2026-02-19-Validation-Measurement)

回归可以分四层看：组件能否加载与校验；轨迹是否出现无效调用、遗漏步骤或副作用；任务交付物是否满足约束；端到端业务是否减少人工返工、提高合格交付率。没有 ground-truth 的生产任务，仍可用可检查的硬约束、抽样人工评审和业务后验指标补证。不要把一段自我评价文本当成独立验收。

发布流程可以很朴素：固定一个不可变配置版本，运行中的任务一直使用启动时的版本；新候选先过回归，再由业务范围或灰度策略选择后续任务使用；发现退化时把版本指针切回旧配置。每份版本都保存来源 task、采用理由、覆盖组件、回归结果与适用范围。以上是本文建议新增的工程层，不是开源仓库自带的生产发布模块。

费用也要分开算。一次优化包括基础执行、两个候选执行、组合后执行、编辑器调用和经验整理；扩大到 $k>1$ 后还会增加探索运行。回归验证也是成本。真正的经济性取决于后续多少相似任务从更好的组件和经验中获益，以及无效调用、重试和人工返工减少多少。可以用一个简单口径跟踪：

> 总成本 = 优化与回归费用 + 后续任务执行费用 + 人工返工费用；同时观察单位合格交付成本、关键约束违反率和 P95 延迟。

适合先试点的任务，通常有一定重复性、能够保存执行轨迹、允许重跑，且外部写操作有测试路径。若任务一次性且实验代价很高，或关键副作用无法隔离，优先建立可观测性和执行协议，比立即开大递归预算更有价值。论文的实验显示 Harness 的改进空间真实存在；业务系统要把它变成持续能力，还需证明这种改进能跨任务复用，并在独立回归与总成本约束下成立。

### 校准说明

- 文中的实验分数来自论文基准，不用于估算 DeerFlow 的业务收益；JobBench 个案的 43.1→77.8 是事后评测结果，不是在线编辑阶段的正确性反馈。

### 名词与概念

- **Execution harness（执行 Harness）**：当前任务运行时加载的提示词、Skills、脚本、工具指引等组件。
- **Improvement harness（改进 Harness）**：引导后续如何修改执行 Harness 的机制及其持久经验库。
- **Probe（探测）**：让候选配置执行相同任务，观察文件编辑带来的行为差异；它本身不证明交付物正确。
- **BenchmarkAdapter（任务适配器）**：Harness² 源码中把任务、执行、轨迹和交付物接入方法核心的接口。
