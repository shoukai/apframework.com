一次问答的结果就在聊天框里。一个需要等待确认、调用外部工具、再把结果带回来的 Agent 任务，完成情况却不能只看最后一句话。进程可能中途退出，跨服务调用可能只留下半段记录，换了模型也可能改变工具选择，即使最终回复看起来没变。

这里说的**长任务**，重点不是运行了多少秒，而是任务能否跨越一次请求或一个进程的生命周期。围绕这类任务，有三个不同的工程问题：**中断后从哪里继续，运行中发生了什么，行为是否符合预期。** 它们分别对应持久执行、遥测与评测。至于外部动作是否真的发生、结果是否正确，还得回到业务系统查证。

**先给结论：能续跑，不等于任务已完成。** 持久执行负责接续流程，遥测提供排查线索，评测检查行为是否符合预期。涉及外部写入时，最终还要查业务系统：动作有没有发生，结果对不对？

如果刚接触这些技术，可以先读第 1 至 3 节；如果正在排查「超时后要不要重试」，可以直接看第 4 节的工单案例。第 5 节的四个问题可以带回自己的项目。

## 1. 持久执行：中断之后，任务如何继续？

对一个中断的任务，先问两件事：**进度记下了吗？谁负责继续？** 只保存数据，和让任务在合适的时机重新运行，是两种不同的责任。

**检查点**（checkpoint）保存某一时刻的执行状态，供应用重新读取。例如，LangGraph 的 checkpointer 按执行线程保存图状态，应用的 store 则可保存跨线程共享的数据。假设检查点里记着“工单负责人尚待确认”，它能让恢复后的程序重新看到这个状态；但仍需要应用监听确认事件，并把事件关联回正确的线程或任务。换句话说，状态持久化回答“上次留下了什么”，调度和唤醒回答“什么时候、由谁继续”。

**持久执行**（durable execution）把可恢复的执行进展交给运行时管理。对调用者来说，流程可以跨越原工作进程的生命周期；进程退出后，运行时依记录恢复流程、等待外部事件或执行配置好的重试。这里的“持久”并非“任务永不失败”，而是把流程进度和执行代码的临时内存分开管理。负责长流程的应用和平台工程师，通常会在需要跨进程恢复、等待外部事件或统一管理重试时考虑这类技术；应用开发者仍要决定哪些操作可重试、怎样处理业务状态。

Temporal 和 Restate 都属于这一问题空间，但保存和重建执行进展的方式不同：

- **Temporal** 的 Workflow 描述流程，Activity 承担调用外部服务等具体动作。Workflow 重新运行时，Temporal 将 Workflow 生成的 Commands 与既有 Event History 对照，通过重放（replay）重建 Workflow 进度；重放不是把所有已完成的 Activity 再调用一次。Activity 如果失败或结果未被可靠记录，仍可能依策略重试。因此官方建议 Activity 尽量具备幂等性——同一动作被再次调用时，不会造成额外业务效果。这个建议是应用侧的设计责任，不是 Temporal 自动为任意外部接口加上的保证。
- **Restate** 把 handler 中受运行时管理的步骤及其结果记录进 journal。恢复时，运行时沿已记录步骤继续，可复用 journal 中已有的结果，而不必重复执行每个已完成步骤。若业务代码在 journal 管理的步骤之外直接调用第三方服务，远端结果与本地执行记录之间仍可能有空档；单看 journal 无法证明这类外部写入是否提交。

因此，看到“工作流恢复成功”还不够。至少要分别确认：运行时恢复到哪一步、外部操作是否会再次调用、业务系统里最终留下几条记录。Temporal 与 Restate 适合在同一故障条件下比较：使用相同输入、外部接口、重试策略和中断位置，再检查各自的事件历史或 journal，以及业务端副作用账本。否则，“都能恢复”既不能说明机制相同，也不能推出外部动作恰好发生一次。

## 2. 遥测：一次任务经过了哪些组件？

排查一次任务时，**追踪能把分散的调用串起来，但只能展示采集到的部分。** 一条用户可见的“超时”消息，并不能告诉你请求究竟停在模型、Agent 进程、MCP 客户端，还是已经抵达工单服务。

**遥测**（telemetry）是软件对外发出的运行信号。常见的三类信号关注点不同：指标适合观察一段时间内的错误率、请求量和延迟分布；日志适合记录带具体上下文的离散事件；追踪（trace）则把一次请求经过的操作串起来。一次追踪由多个 span 组成，每个 span 记录一项操作的时间、属性和状态等信息。它们互相补充：指标可以提示某服务整体变慢，trace 帮你定位某次调用经过哪里，日志则补充该步骤的具体事件。

**OpenTelemetry（OTel）**提供开放的遥测规范、API 和 SDK。它不是自动观察所有组件的探针：应用和依赖需要埋点并导出信号；跨服务时，还要传播追踪上下文，服务端 span 才能与客户端调用关联。对负责集成的工程师，这意味着要逐段核对模型调用、Agent、工具客户端和工具服务是否都记录了预期 span，属性是否足以排查，又有没有采集不该外传的内容。

如果工具通过 **MCP**（Model Context Protocol，模型上下文协议）接入，MCP 解决的是 AI 应用如何与工具或数据服务交互。它不是遥测规范，也不替应用保证 trace context 已跨进程传播。一次 MCP 调用即使成功返回，是否完成业务提交仍取决于具体工具接口的语义；是否能在追踪中看到整条路径，则取决于两端的埋点、导出和上下文传递。

因此，一条 trace 首先是**已采集到的证据**，不是整个现实的录像。没有服务端 span，可能是请求没到，也可能是未埋点、未采集、导出失败或上下文断开。看见成功响应也只能说明对应接口报告了成功；若要确认工单已经创建且分派正确，仍需查询工单系统。可观测性工程师据此缩小排查范围，不能把“没有记录”直接当成“没有发生”。

## 3. 评测：换了模型或提示词，行为还是对的吗？

**评测**（evaluation）是把“应该怎么做”变成可检查的预期。只看最后答案，可能漏掉过程中的错误：Agent 虽然给出了“已提交”的自然语言回复，却没有调用创建工具；也可能调用了正确工具，却把错误的项目或负责人传了进去。对会采取行动的 Agent，至少要区分三类检查：结果是否满足用户目标、工具选择与参数是否符合预期、必要步骤和先后顺序是否正确。

**Promptfoo** 是评测工具。Agent 开发者和测试工程师可以编写用例，并通过轨迹断言（trajectory assertion）检查记录到的工具、参数或步骤，例如“应先查询相似工单，再等待负责人确认，最后才允许创建”，或“创建参数中的项目必须与确认内容一致”。这些断言把原本隐含的行为要求变成可重复检查的条件；它们检查的是被记录的执行轨迹，不是自动接管工具权限或业务事务。

OpenTelemetry 与 Promptfoo 因而可以协作，但职责不同：配置相应埋点和采集后，OTel 轨迹可提供执行记录，Promptfoo 的用例和断言再判断记录是否符合预期。轨迹覆盖不足时，断言的结论也受限；测试用例通过，只表示这组输入和观测到的行为满足了所写条件，不表示生产环境每次运行都正确，也不证明第三方业务系统已完成写入。涉及“绝不在确认前创建”这类约束，仍应由工作流或工具服务执行时强制；评测用于发现回归、验证测试路径是否遵守约束。

![遥测轨迹和测试预期共同进入行为断言](/static/images/2026-11-27-agent-long-running-work-reliability-overview/trace-to-eval.svg)

*图 2：遥测记录测试中发生的操作，断言将它与用例的预期比对。两者都不能确认工单是否写入。*

## 4. 一张工单，到底建成没有？

### 4.1 本地没有完成记录，远端可能已经写入

假设工程团队收到一条反馈：“登录一直转圈，重试后偶尔恢复。”Agent 从讨论中整理现象，查找相似工单，并建议分给身份认证团队。负责人确认项目、归属和摘要后，工作流才调用外部工单服务。这类交互已有产品示例：[Atlassian 的 Rovo 文档](https://support.atlassian.com/rovo/docs/using-the-atlassian-rovo-slack-app/)展示了从 Slack 对话确认并创建 Jira 工作项；下面的故障是一个假设场景，不是对 Rovo 实现的描述。

工单服务已经创建记录，但工作进程在保存返回的工单号之前退出。恢复时，执行记录里只有“已确认”和“开始创建”，没有“创建完成”。对恢复的进程而言，请求没到服务端、服务端已经写入但响应丢失、进程收到响应却没来得及保存，都可能留下相同的本地状态：**结果未知**。

![工单创建的远端提交与本地确认窗口](/static/images/2026-11-27-agent-long-running-work-reliability-overview/d1.svg)

*图 3：工单服务已写入，但执行器还没保存工单号。本地缺少完成记录，不等于远端没执行。*

### 4.2 四个问题，分别查哪份记录？

同一个故障，执行历史、追踪、测试结果和工单记录分别能回答不同的问题。关键不是找一条“最权威”的日志，而是让每种记录只回答它能支持的问题：

| 要回答的问题 | 查什么 | 不能从中推出什么 |
| --- | --- | --- |
| 流程从哪里继续？ | 看 Temporal 事件历史或 Restate journal 中的确认记录、建单步骤和已保存结果 | 建单尚未记为完成，不等于远端没有创建 |
| 运行中发生了什么？ | 看 Agent、工具服务和工单接口的 span，定位最后一个可见操作 | 响应 span 缺失，不等于请求失败 |
| Agent 是否按要求行动？ | 用 Promptfoo 检查测试轨迹：是否查重、是否在确认后尝试写入、参数是否符合确认内容 | 断言通过，不等于工单已写入，也不是生产权限控制 |
| 业务目标是否达成？ | 查工单系统：这次请求对应几张单、项目和分派是否正确 | 结果正确，不代表过程遵守了所有规则 |

这里有两个容易混淆的“去重”。Agent **查找相似工单**，是为了判断两条反馈是否属于同一个问题，属于业务检索与判断；恢复时复用**幂等键（idempotency key）**，是为了让支持该语义的接口把同一个已确认的创建动作识别为重复提交，属于写入去重机制。前者可能漏掉重复单，也可能把不同问题误判为相似，不能代替后者；后者也不能替你判断两个用户反馈是不是同一个故障。

幂等键需要在首次提交前稳定生成，并与这次获批的动作绑定；重试时复用原键，而不是每次尝试换新键。它是否有效，还要看工单接口是否实现该约定、作用范围和有效期是什么，以及相同键但不同参数时服务如何处理。若服务不支持幂等键，就不能只在 Agent 侧生成一个字符串便宣称安全重试。

同样，“必须先经负责人确认”不能只写在提示词或测试断言里。工作流可以在确认事件到达前不进入创建步骤，工具服务也可要求有效的审批凭证；Promptfoo 则用测试轨迹检查测试场景里是否遵守顺序。测试能发现回归，但真正的执行边界仍要由运行系统强制。

### 4.3 恢复时，先决定能不能重试

面对“本地没有工单号”的恢复请求，不要立刻把它当作失败，也不要因为“恢复运行成功”就直接再建一张。先按系统能提供的证据，区分已确认、已拒绝和仍未知：

1. **固定动作身份。** 负责人确认后，为这次建单动作建立稳定标识，并在请求前保存到可恢复的流程记录中。后续重试沿用同一标识和同一组已确认参数，避免把一次动作的不同尝试误当成多次新操作。
2. **查询远端结果。** 若工单服务支持按动作标识查询，读取对应记录并核对工单号、项目、负责人和摘要。确认匹配后补写本地完成记录，不再新建。查询也要考虑服务的可见性延迟：一次未命中可能只是索引尚未更新，不能单凭它证明记录不存在。
3. **只在接口语义明确时重试。** 若接口明确支持该标识的幂等提交，且仍在其作用范围和有效期内，可按约定使用原键、原参数重试。若接口不支持查询，也没有可靠幂等保证，就保留“结果待确认”，稍后复查或转人工，不要用盲目重试把不确定性变成重复副作用。
4. **核对业务目标再结束。** 只有拿到远端工单号并核对项目、负责人等关键字段后，才报告建单完成。若记录存在但字段与确认内容不符，应进入纠错流程，而不是将“创建成功”当作“任务正确”。

换成电商退款，问题的结构不变：远端可能已经提交，本地还没记录。不同的是重复动作的后果，以及自动重试所需的授权和确认条件。对于大额退款等高风险动作，[OpenAI 的 Agent 构建指南](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents)建议考虑人工监督。工单适合讲清机制；退款则提醒我们，同样的恢复策略不能不加判断地搬到不同业务里。

## 5. 用四个问题检查自己的任务

挑一个需要等待或会写入外部系统的动作，试着写下四个答案：

- **恢复：** 中断后，靠哪条记录继续？
- **观测：** 调用超时，到哪里看最后一个已记录的操作？
- **评测：** 更换模型或提示词后，用哪个测试用例检查行为有没有退步？
- **结果：** 到哪个业务系统确认动作已经执行，结果也符合预期？

把答案写成一张小型证据表，会比笼统地说“系统可恢复、全链路可观测、Agent 已通过评测”更有用：每项能力分别记录其数据来源、覆盖范围、缺口和负责人。这样在事故处理中，团队能明确下一步该查执行历史、补充遥测，还是由业务系统管理员核对实际记录。

不必为四个问题都引进新工具。短时、只读的任务也许不需要专门的持久执行平台；但只要一次外部写入可能成功而本地不知情，就要先确定结果未知时如何查证、何时允许重试。

这也是这些技术放在一起讨论的理由：Temporal 和 Restate 面对同一类执行问题，可以共享故障实验；OpenTelemetry 和 Promptfoo 则分别记录过程和检查预期，可以协作，却不适合做同类工具排名。无论选哪套工具，一张工单是否建对，最终仍要由工单系统里的记录回答。
